Loggy · Implementation Details

회의 의사결정 과정을 구조화하는 실시간 협업 서비스

Loggy는 회의에서 나온 논의를 안건, 브랜치, 커밋 흐름으로 연결해 기록하고, 회의 종료 후에도 결정 근거를 추적할 수 있도록 만든 협업 서비스입니다. 일반 채팅은 Redis에 휘발성으로 저장하고, 의미 있는 채팅과 결정 기록은 DB에 영속화해 실시간성과 추적성을 동시에 확보했습니다. 저는 회의, 안건, 브랜치, 알림 도메인 백엔드를 담당하며 인증/인가, 실시간 채팅 정책, 알림, 집계 API를 설계·구현했습니다.

Implementation Details

JWT 기반 인증/인가 구조 정리

문제

기능 구현이 먼저 진행되면 회의, 안건, 브랜치 접근 제어가 기능별로 흩어지고 예외 케이스가 늘어나기 쉽습니다.

해결

JWT 사용자 정보를 직접 주입받고, 서비스 계층에서 팀원 여부 → 참가자 여부 → 소유자 여부 순으로 검증했습니다.

성과

기능 구현이 아니라 권한 모델 설계 관점으로 설명할 수 있는 인가 흐름을 도메인 전반에 통일했습니다.

@GetMapping("/{meetingId}")
public BaseResponse<MeetingDetailResponse> getMeeting(
        @AuthenticationPrincipal CustomUserDetails userDetails,
        @PathVariable Long meetingId
) {
    return BaseResponse.success(meetingService.getMeeting(userDetails.getUserId(), meetingId));
}

private void validateTeamMember(Long userId, Long teamId) {

    }
}

Redis + DB 하이브리드 채팅 구조 리팩토링

문제

Redis만 보면 과거 문맥이 끊기고, 모든 메시지를 영구 저장하면 비용과 의미 관리가 어려워졌습니다.

해결

일반 채팅과 기록 채팅을 분리하고, 진행 중인 대상은 Redis+DB 병합 조회, 종료된 대상은 DB만 조회하도록 정리했습니다.

성과

실시간성과 추적성을 함께 확보하면서 종료 이후 데이터 정책도 단순하게 정리했습니다.

List<ChatMessageDto> merged = mergeBySeq(dbMessages, redisMessages);
return applyCursorAndLimit(merged, cursorSeq, direction, size);

private List<ChatMessageDto> mergeBySeq(List<ChatMessageDto> dbMessages, List<ChatMessageDto> redisMessages) {
    Map<Long, ChatMessageDto> mergedMap = new LinkedHashMap<>();
    dbMessages.forEach(message -> mergedMap.put(message.getSeq(), message));
    redisMessages.forEach(message -> mergedMap.put(message.getSeq(), message));
    return mergedMap.values().stream()
            .sorted(Comparator.comparingLong(ChatMessageDto::getSeq))
            .toList();
}

실시간 알림 시스템 구현

문제

회의 초대, 회의 시작, 브랜치 생성, 안건 재오픈 같은 이벤트는 조회형 알림만으로는 즉시성이 부족했습니다.

해결

알림을 DB에 저장해 이력을 남기고, 동시에 WebSocket으로 즉시 푸시하도록 구현했습니다.

성과

사용자는 중요한 이벤트를 즉시 확인하고, 나중에 다시 들어와도 동일한 이력을 조회할 수 있게 됐습니다.

Notification saved = notificationRepository.save(notification);
NotificationResponse response = NotificationResponse.from(saved, notification.getTeamId());
webSocketPublisher.publish(saved.getReceiverId(), response);

관계형 데이터 조회 최적화

문제

회의 상세, 안건 트리, 브랜치별 기록 화면은 연관 데이터가 많아 단순 구현 시 반복 조회가 빠르게 증가했습니다.

해결

참가자 정보는 배치 조회 후 메모리 매핑하고, 안건 계층 구조는 전체 조회 후 parent-child를 메모리에서 조립했습니다.

성과

응답 구조 중심으로 조회 전략을 설계한 사례가 되었고, 화면 요구사항에 맞는 데이터 조립 경험을 확보했습니다.

Map<Long, User> userMap = userRepository.findByIdIn(userIds).stream()
        .collect(Collectors.toMap(User::getId, user -> user));

Map<Long, List<IssueNodeResponse>> childrenMap = issueTree.stream()
        .collect(Collectors.groupingBy(node -> Optional.ofNullable(node.parentIssueId()).orElse(0L)));
