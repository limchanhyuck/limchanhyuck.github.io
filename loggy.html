Loggy Backend Case Study

회의 의사결정 흐름을 추적 가능한 협업 도메인으로 설계

Loggy는 회의 중 발생한 논의를 Meeting, Issue, Branch 단위로 구조화하고, 실시간 채팅과 결정 근거를 함께 남기는 협업 서비스입니다. 담당 범위는 Meeting, Issue, Branch, Notification 백엔드 도메인이며, 단순 API 나열보다 권한 경계, 조회 성능, Redis와 DB 데이터 생명주기 분리, 테스트 체계 구축에 집중했습니다.

Role

직접 구현/개선한 범위

  • Meeting: 회의 생성, 참여자 검증, 시작/종료 상태 전이, 회의 상태 이벤트 전파
  • Issue: 계층형 안건 응답, 담당자 권한 검증, 재오픈 시 기존 결정 기록 삭제
  • Branch: 브랜치 제안, 작성자/활동량 응답, 채택/기각 상태 전이
  • Notification: 알림 생성, 목록 조회, 읽음/삭제, 미읽음 카운트, WebSocket 전송
  • Chat 리팩터링: Redis 임시 메시지와 DB 영구 메시지 병합 조회 구조
  • 테스트: 인증 컨텍스트 공통 주입과 Controller/WebSocket/Service 테스트 구축

팀 공통 범위로 분리할 내용

  • DB 스키마 전체 설계는 팀 공통 범위로만 언급
  • 인증/보안 전체 전환은 직접 성과가 아닌 보조 맥락으로 처리
  • AI 결정문 생성과 프론트엔드 UI는 직접 기여 핵심에서 제외
  • Controller CRUD, DTO 추가, enum 추가는 포트폴리오 메인 성과에서 제외
Core Logic

1. 상위 협업 컨텍스트 기준 권한 경계 통일

pain point 회의 참여자, 안건 담당자, 브랜치 작성자의 권한 기준이 섞이면 잘못된 사용자가 상태 변경을 수행할 수 있습니다.
solution Meeting은 팀/회의 멤버를 분리 검증하고, Issue와 Branch는 meeting membership을 기준으로 접근을 제한했습니다.
impact Meeting, Issue, Branch 도메인의 접근 제어 기준을 한 방향으로 정리했습니다.
코드 스니펫 
private void validateMeetingMember(Long meetingId, Long userId) {
    if (!meetingMemberRepository.existsByMeetingIdAndUserId(meetingId, userId)) {
        throw new CustomException(ErrorCode.MEETING_NOT_MEMBER);
    }
}

2. 리스트 응답의 N+1 위험을 집계 쿼리로 제거

pain point 회의/안건/브랜치 목록은 항목마다 참여자 수, 브랜치 수, 작성자 정보를 함께 내려줘야 했습니다.
solution `countByMeetingIdIn`, `countByIssueIds`, `findByIdIn`으로 반복 조회를 일괄 조회로 바꿨습니다.
impact 목록 크기 N에 비례하던 count/user 조회를 집계 1회와 일괄 조회 1회 패턴으로 정리했습니다.
코드 스니펫 
Map<Long, Long> branchCountMap = branchRepository.countByIssueIds(issueIds).stream()
        .collect(Collectors.toMap(
                row -> (Long) row[0],
                row -> (Long) row[1]
        ));

3. Redis 임시 채팅과 DB 영구 채팅 병합

pain point 일반 채팅은 실시간성이 중요하고, 질문/의견/TODO는 회의 후에도 근거로 남아야 했습니다.
solution 일반 메시지는 Redis에 두고, 의미 있는 Issue/Branch 메시지는 DB에 저장한 뒤 `seq` 기준으로 병합했습니다.
impact 실시간 UX와 의사결정 근거 보존을 저장 계층에서 분리했습니다.
코드 스니펫 
for (ChatMessageDto msg : redis) {
    if (msg.getSeq() != null) {
        map.put(msg.getSeq(), msg);
    }
}
for (ChatMessageDto msg : db) {
    if (msg.getSeq() != null) {
        map.put(msg.getSeq(), msg);
    }
}

4. 알림 도메인을 이벤트 소비 책임으로 분리

pain point 회의 초대, 회의 시작, 안건 생성, 브랜치 제안은 모두 알림이 필요하지만 핵심 상태 변경과 강하게 결합되면 유지보수가 어려워집니다.
solution `NotificationCreateCommand`로 알림 생성을 표준화하고, 저장 후 WebSocket Publisher로 전송했습니다.
impact 알림 생성, 조회, 읽음, 삭제, 미읽음 카운트를 독립 도메인으로 운영할 수 있게 했습니다.
코드 스니펫 
notificationRepository.save(notification);

Long teamId = resolveTeamId(notification);
NotificationResponse response = NotificationResponse.from(notification, teamId);
notificationPublisher.send(command.getUserId(), response);

5. 인증 컨텍스트 테스트 공통화

pain point 권한과 상태 조건이 많은 도메인은 컨트롤러 테스트마다 인증 주입 코드가 반복되기 쉽습니다.
solution `BaseWebMvcTest`와 `TestAuth`를 만들어 JWT 필터와 SecurityContext 주입을 공통화했습니다.
impact 핵심 도메인 테스트 기준 `@Test` 115개로 정상/예외 흐름을 회귀 방어했습니다.
코드 스니펫 
public static RequestPostProcessor user(Long id) {
    return request -> {
        CustomUserDetails details = userDetails(id);
        Authentication authentication =
                new UsernamePasswordAuthenticationToken(details, null, details.getAuthorities());
        SecurityContextHolder.getContext().setAuthentication(authentication);
        request.setUserPrincipal(authentication);
        return request;
    };
}
Interview Focus
  • JWT 자체보다 meeting membership을 기준으로 도메인 접근 경계를 통일한 점
  • 리스트 화면의 count/user 반복 조회를 batch aggregation으로 줄인 점
  • Redis와 DB를 기술 선택이 아니라 데이터 생명주기 정책으로 나눈 점
  • 알림을 핵심 도메인 상태 변경과 분리해 저장/전송 책임을 독립시킨 점
  • Controller/WebSocket/Service 테스트를 인증 공통 헬퍼 위에 올려 회귀 안정성을 확보한 점
