Loggy Backend Case Study

회의 의사결정 흐름을 추적 가능한 협업 도메인으로 설계

Loggy는 회의 중 발생한 논의를 Meeting, Issue, Branch 단위로 구조화하고, 실시간 채팅과 결정 근거를 함께 남기는 협업 서비스입니다. 담당 범위는 Meeting, Issue, Branch, Notification 백엔드 도메인이며, 단순 API 나열보다 권한 경계, 조회 성능, Redis와 DB 데이터 생명주기 분리, 테스트 체계 구축에 집중했습니다.

Spring Boot Java 17 PostgreSQL Redis WebSocket/STOMP Spring Security

Role

직접 구현/개선한 범위

  • Meeting: 회의 생성, 참여자 검증, 시작/종료 상태 전이, 회의 상태 이벤트 전파
  • Issue: 계층형 안건 응답, 담당자 권한 검증, 재오픈 시 기존 결정 기록 삭제
  • Branch: 브랜치 제안, 작성자/활동량 응답, 채택/기각 상태 전이
  • Notification: 알림 생성, 목록 조회, 읽음/삭제, 미읽음 카운트, WebSocket 전송
  • Chat 리팩터링: Redis 임시 메시지와 DB 영구 메시지 병합 조회 구조
  • 테스트: 인증 컨텍스트 공통 주입과 Controller/WebSocket/Service 테스트 구축

팀 공통/연동 맥락

  • DB 스키마와 인증/보안 전환은 팀 공통 설계 맥락으로 연결
  • AI 결정문 생성과 프론트엔드 UI는 Meeting·Issue·Branch 흐름과 연동되는 인접 도메인으로 구분
  • Controller CRUD, DTO, enum은 핵심 성과가 아니라 도메인 흐름을 설명하는 보조 구현으로 정리
핵심 구현 흐름

1. Meeting 목록 조회 N+1 제거

문제 회의 목록은 회의마다 참여자 수와 생성자 정보를 함께 보여줘야 해서 항목별 count/user 조회가 반복될 수 있습니다.
해결 목록의 meetingId와 userId를 먼저 모은 뒤 `countByMeetingIdIn`, `findByIdIn`으로 집계/사용자 조회를 일괄 처리했습니다.
성과 회의 20개 기준 참여자 count 최대 20회 → 집계 1회, 생성자 조회 최대 20회 → IN 조회 1회 구조로 줄였습니다.

2. Chat / Issue 메시지 보존 구조

문제 일반 채팅은 빠르게 처리해야 하고, 질문/답변/TODO는 회의 후에도 근거로 남아야 했습니다.
해결 일반 메시지는 Redis에 두고, 의사결정성 메시지는 DB에 저장한 뒤 `seq` 기준으로 병합했습니다.
성과 Redis/DB 2개 저장소를 유지하면서 클라이언트에는 `seq` 기준 1개 타임라인으로 병합해 내려주도록 정리했습니다.

3. Branch 결정 제안 생성

문제 회의 중 나온 의견을 결정 후보로 올릴 때 같은 안건 안에서 중복된 제안이 생기면 최종 결정 추적이 어려워집니다.
해결 Issue 하위 Branch 이름 중복을 먼저 차단하고, 선택된 의견을 근거로 연결해 결정 제안을 생성했습니다.
성과 저장 전 `issueId + name` 1회 검증으로 같은 안건 안의 중복 결정 후보 생성을 차단했습니다.

4. History 목록 조회 최적화

문제 회의 히스토리는 메시지, 작성자, 안건, 브랜치 상태가 함께 표시되어 목록 크기 N에 따라 반복 조회가 커질 수 있습니다.
해결 `countByIssueIds`, `findByIdIn`처럼 ID를 모아 집계 조회와 IN 조회로 필요한 데이터를 한 번에 가져왔습니다.
성과 안건 20개 기준 브랜치 수 조회 최대 20회 → 집계 1회, 작성자 조회 최대 20회 → IN 조회 1회 패턴으로 줄였습니다.

5. Meeting Record와 회귀 테스트

문제 회의록, TODO, 최종 결정 요약은 권한과 상태 조건이 많아 회의 종료 후 회귀가 발생하기 쉬운 영역입니다.
해결 `BaseWebMvcTest`, `TestAuth`로 인증 컨텍스트 주입을 공통화하고 핵심 도메인 테스트를 구성했습니다.
성과 핵심 Controller/WebSocket 매핑 29개와 핵심 도메인 `@Test` 115개 기준으로 정상/예외 흐름을 검증했습니다.
Interview Focus
  • JWT 자체보다 meeting membership을 기준으로 도메인 접근 경계를 통일한 점
  • 리스트 화면의 count/user 반복 조회를 batch aggregation으로 줄인 점
  • Redis와 DB를 기술 선택이 아니라 데이터 생명주기 정책으로 나눈 점
  • 알림을 핵심 도메인 상태 변경과 분리해 저장/전송 책임을 독립시킨 점
  • Controller/WebSocket/Service 테스트를 인증 공통 헬퍼 위에 올려 회귀 안정성을 확보한 점
