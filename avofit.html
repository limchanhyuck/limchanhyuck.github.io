Avofit · Implementation Details

AI 식단 생성 지연과 LLM 불안정을 서비스 로직으로 통제한 다이어트 코치

Avofit은 사용자 TDEE, 목표 칼로리, 선호/알레르기, 월간 예산을 기반으로 30일 식단을 생성하고 장보기 추천까지 연결하는 다이어트 코치 서비스입니다. 핵심은 AI를 붙인 것이 아니라, 식단 생성 지연은 7일 선응답 + 23일 비동기 병렬 처리로, 불안정한 LLM 응답은 재시도 + JSON 정제 + 템플릿 fallback으로 흡수했다는 점입니다.

Implementation Details

AI 식단 생성 지연을 7일 선응답 + 23일 병렬 처리로 분해

문제

30일 전체 식단을 한 번에 생성하면 첫 응답이 늦어지고, 사용자는 결과가 나오기 전까지 아무것도 확인할 수 없었습니다.

해결

첫 7일만 동기 생성해 먼저 반환하고, 나머지 23일은 CompletableFuture로 주차 단위 병렬 처리했습니다.

성과

초기 체감 속도를 확보하면서도 월간 식단 전체를 포기하지 않는 응답 구조를 만들었습니다.

generateAndSaveChunk(mealPlan, allDays, basePayload, 0, 7, targetKcalPerDay, mealsPerDay);

CompletableFuture.runAsync(() -> {
    try {
        generateRemainingWeeksParallel(mealPlan, allDays, basePayload, targetKcalPerDay, mealsPerDay);
    } catch (Exception e) {
        log.error("[MealPlan] Async generation failed for planId={}", mealPlan.getId(), e);
    }
});

for (int offset = 7; offset < DEFAULT_PLAN_DAYS; offset += AI_CHUNK_DAYS) {
    int currentOffset = offset;
    int limit = Math.min(AI_CHUNK_DAYS, DEFAULT_PLAN_DAYS - currentOffset);
    futures.add(CompletableFuture.runAsync(() ->
        generateAndSaveChunk(mealPlan, allDays, basePayload, currentOffset, limit, targetKcal, mealsPerDay)
    ));
}

LLM 불안정성을 재시도와 JSON 정제로 흡수

문제

LLM 응답은 빈 값이 오거나, 마크다운 코드블록이 섞이거나, JSON 외 텍스트가 붙어 파싱이 깨질 수 있었습니다.

해결

DietAiClient에서 2회 재시도 후 JSON만 추출하고, 서비스 레이어가 후속 fallback으로 이어받을 수 있게 분리했습니다.

성과

AI 출력 품질이 흔들려도 식단 생성 API 자체는 계속 결과를 반환하는 안정적인 파이프라인이 됐습니다.

public AiMonthlySkeletonResponse generateMonthlySkeleton(Map<String, Object> payload) {

        return callOnce(payload);
    } catch (Exception first) {
        log.warn("[AI] first attempt failed: {}", first.getMessage());
        try {
            return callOnce(payload);
        } catch (Exception second) {
            throw new RuntimeException("AI_CALL_FAILED", second);
        }
    }
}

AI 실패를 템플릿 식단과 칼로리 스케일링으로 복구

문제

AI 식단이 실패하거나 칼로리가 목표치에서 크게 벗어나면, 추천 품질이 흔들리고 하루 총량도 무너질 수 있었습니다.

해결

AI 실패 시 템플릿 식단으로 내려가고, 생성 결과가 목표 칼로리 범위를 벗어나면 grams를 재계산해 전체 칼로리를 다시 맞췄습니다.

성과

AI가 흔들려도 서비스 결과는 비지니스 규칙 안으로 다시 들어오게 만들어 식단 일관성을 지켰습니다.

장보기 추천을 검색이 아니라 예산 제약 최적화로 설계

문제

식단 재료 검색 결과를 단순 상단 노출 순서대로 고르면 예산 초과 상품이나 부정확한 후보가 선택될 수 있었습니다.

해결

정규화 검색, 카테고리 보정, scorer 기반 후보 추리기, AI rerank, 실패 시 fallback, 최종 BUDGET_GUARD를 연결했습니다.

성과

추천 품질과 예산 적합성을 동시에 챙기면서도, AI 실패 시 규칙 기반 결과로 안전하게 내려오도록 만들었습니다.

List<ShoppingProduct> topCandidates =
    productScorer.selectTopN(products, ingredientName, allocatedBudget, totalGram, 10);

if (topCandidates.size() >= 3) {
    try {
        ShoppingProduct aiSelected = aiReranker.rerank(ingredientName, allocatedBudget, topCandidates);
        best = (aiSelected != null) ? aiSelected : topCandidates.get(0);
        reason = (aiSelected != null) ? "AI_SELECTED" : "AI_FAIL_FALLBACK";
    } catch (Exception e) {
        best = topCandidates.get(0);
        reason = "AI_ERROR_FALLBACK";
    }
}

BudgetGuardResult guarded =
    enforceBudgetFit(ingredientName, allocatedBudget, totalGram, topCandidates, best, reason);
best = guarded.product();
reason = guarded.reason();

JWT 인증을 발급에서 끝내지 않고 refresh rotation까지 적용

문제

Refresh token을 평문 저장하거나 재사용 가능하게 두면 탈취 시 세션이 길게 악용될 위험이 있었습니다.

해결

Refresh token은 SHA-256 해시만 DB에 저장하고, refresh 요청 시 검증 후 기존 토큰을 revoke한 뒤 새 토큰 쌍을 발급했습니다.

성과

토큰 재사용 위험을 줄이고, access/refresh 수명 분리와 함께 인증 보안 설계의 완성도를 높였습니다.

String tokenHash = TokenHasher.sha256(token);
RefreshToken saved = refreshTokenMapper.findByTokenHash(tokenHash);

if (Boolean.TRUE.equals(saved.getRevoked())) {
    throw new BusinessException("Refresh token revoked");
}

refreshTokenMapper.revokeById(saved.getId());

String newAccess = jwtTokenProvider.createAccessToken(userId);
String newRefresh = jwtTokenProvider.createRefreshToken(userId);

refreshTokenMapper.insert(RefreshToken.builder()
    .userId(userId)
    .tokenHash(TokenHasher.sha256(newRefresh))
    .expiresAt(jwtTokenProvider.getExpiry(newRefresh))
    .revoked(false)
    .build());
