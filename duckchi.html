중복 요청과 부분 실패를 제어한 정산 백엔드 설계

Duckchi는 모임 정산을 빠르게 끝내고, 정산 이후에도 소비 데이터를 남겨 분석까지 연결하는 더치페이 서비스입니다. Pay Service에서 모임·정산 백엔드를 담당하며, 정산 요청 생성부터 다건 송금, 수동 완료, 대기/상세 조회까지 정산의 핵심 생애주기를 설계·구현했습니다.

Overview

담당 범위

  • Pay Service에서 정산 요청 생성, 다건 송금, 수동 완료, 정산 상세/대기 조회 API를 설계·구현
  • 결제건 기준 정산 생성, 송금 실행, 정산 상태 전이, 권한·멤버십 검증을 서버 규칙으로 정리
  • 외부 금융 API 실패를 정산 도메인 에러로 복원하고 재시도 가능한 실패 ID를 응답에 포함
  • room/settlement 조회에서 반복 조회를 배치 조회로 바꿔 목록·상세 응답 비용을 낮춤

핵심 지표

  • Room/Settlement 중심 백엔드 API 13개를 맡아 정산 요청부터 송금 완료까지 연결
  • settlements UNIQUE 3종으로 결제건·사용자·금융 요청번호 단위 중복 반영 차단
  • 최대 30건 다건 송금을 건별 독립 트랜잭션으로 분리해 실패 건만 재처리 가능
  • room/settlement 도메인 테스트 파일 19개로 중복 요청, 부분 실패, 잔액 부족, 재시도 흐름 검증
문제 정의

정산 실패를 복구 가능한 상태로 분리

정산은 같은 결제건에 대한 중복 요청, 여러 명에게 보내는 송금 중 일부 실패, 외부 금융망 재시도, 잔액 부족이 동시에 발생할 수 있는 흐름입니다. 이 문제를 하나의 실패로 묶으면 이미 성공한 송금까지 다시 처리해야 하고, 사용자는 무엇을 해결해야 하는지 알기 어렵습니다. Duckchi Pay Service는 중복 생성은 잠금과 DB 제약으로 막고, 송금 실패는 건별 트랜잭션과 실패 ID로 분리해 성공 건은 보존하고 실패 건만 다시 처리하도록 설계했습니다.

Implementation Details

중복 정산 요청을 잠금 + UNIQUE 3종으로 차단

문제

동일 결제건에 대해 정산 요청이 동시에 들어오면 같은 payer에 대한 settlement가 중복 생성될 수 있었습니다.

해결

요청 ID를 정규화한 뒤 결제건을 FOR UPDATE로 잠그고, 저장 직후 flush로 UNIQUE 위반을 즉시 감지했습니다.

성과

서비스 계층 검증과 DB UNIQUE 3종을 함께 적용해 중복 정산 생성과 중복 금융 요청을 이중 차단했습니다.

다건 송금 실패를 건별 트랜잭션으로 격리

문제

여러 계좌로 한 번에 송금할 때 1건 실패가 전체 롤백으로 번지면 성공 가능한 정산까지 모두 다시 처리해야 했습니다.

해결

각 settlement 송금을 REQUIRES_NEW 트랜잭션으로 실행하고 실패 ID만 수집해 부분 성공 응답으로 분리했습니다.

성과

5건 중 1건이 실패해도 4건은 완료 상태로 보존하고, 실패한 1건만 재처리할 수 있는 구조가 되었습니다.

금융망 재시도 멱등키를 선커밋

문제

외부 금융망 호출 후 네트워크 실패가 발생하면 재시도 과정에서 같은 송금이 중복 반영될 위험이 있었습니다.

해결

finance_request_unique_no를 별도 트랜잭션에서 먼저 확정하고, 이후 재시도는 기존 키를 재사용하게 했습니다.

성과

금융 요청번호 UNIQUE 제약과 멱등키 재사용으로 같은 settlement의 중복 송금 요청을 차단했습니다.

잔액 부족을 일반 부분 실패와 분리

문제

금융 API의 잔액 부족 코드가 일반 부분 실패로 묶이면 사용자는 충전이 필요한 상황인지 재시도가 필요한 상황인지 구분할 수 없었습니다.

해결

금융 API의 잔액 부족 응답을 정상 응답과 예외 응답 양쪽에서 감지하고, 일반 부분 실패보다 우선 처리했습니다.

성과

혼합 실패 상황에서도 잔액 부족은 충전 안내로, 그 외 일부 실패는 실패 건 재시도 안내로 분리해 사용자의 다음 행동을 명확히 했습니다.

정산 조회 반복 조회를 배치 조회로 축소

문제

정산 대기 목록은 결제 제목과 참여자 수가 함께 필요해 항목별 조회가 반복되면 N+1 형태로 커질 수 있었습니다.

해결

expenseIds를 모아 제목과 참여자 수를 각각 한 번의 배치 조회로 가져오고 Map으로 조립했습니다.

성과

N개 정산 항목 기준 제목 N회 + 참여자 수 N회 반복 조회 가능성을 2회 배치 조회로 줄였습니다.
