Loggy · Implementation Details

기술 의사결정 과정을 구조화하는 실시간 협업 서비스

Loggy는 회의에서 나온 논의를 안건과 브랜치 흐름으로 연결해 기록하고, 이후에도 결정 근거를 추적할 수 있도록 만든 협업 서비스입니다. 저는 이 프로젝트에서 Meeting, Issue, Branch, Notification 도메인 백엔드를 담당하며, 회의 생성부터 안건 구조화, 브랜치 제안 관리, 알림 전달까지 협업 흐름의 핵심 API를 설계·구현했습니다. 단순 CRUD가 아니라 도메인 규칙에 맞는 권한 검증, 계층형 데이터 응답, 실시간 이벤트 전달까지 포함해 협업 서비스의 실제 운영 흐름을 백엔드 관점에서 정리한 경험이 핵심입니다.

Implementation Details

도메인 규칙에 맞는 권한 검증 구조 정리

문제

협업 서비스는 같은 팀인지, 같은 회의 참가자인지, 소유자인지에 따라 허용되는 동작이 달라져 접근 제어가 쉽게 흐트러질 수 있습니다.

해결

JWT 사용자 정보를 주입받고, 서비스 계층에서 팀 멤버 여부, 회의 참가 여부, 소유자 여부를 단계적으로 검증하도록 정리했습니다.

성과

Meeting, Issue, Branch, Notification API 전반에서 접근 제어 기준이 일관되게 유지되도록 만들었습니다.

@PostMapping("/teams/{teamId}/meetings")
public ResponseEntity<ApiResponseDto<MeetingResponse>> createMeeting(
        @PathVariable Long teamId,
        @RequestBody @Valid MeetingCreateRequest request,
        @AuthenticationPrincipal CustomUserDetails userDetails) {
    Long userId = userDetails.getUser().getId();
    return ResponseEntity.status(HttpStatus.CREATED)
            .body(ApiResponseDto.success(meetingService.create(teamId, userId, request)));
}

private void validateMeetingMember(Long meetingId, Long userId) {
    if (!meetingMemberRepository.existsByMeetingIdAndUserId(meetingId, userId)) {
        throw new CustomException(ErrorCode.MEETING_NOT_MEMBER);
    }
}

회의 라이프사이클 API 설계

문제

회의는 생성자와 참여자 등록, 입장 검증, 시작/종료 상태 전이, 초대 알림 등 여러 행위가 연결되어 상태 해석이 어긋나기 쉬웠습니다.

해결

회의 생성 시 팀 멤버를 먼저 검증하고, 생성자는 OWNER, 초대된 사용자는 MEMBER로 등록했습니다. 시작/종료는 소유자만 실행하도록 제한했습니다.

성과

회의 도메인의 핵심 상태 흐름을 백엔드가 명확하게 책임지는 구조를 만들었습니다.

Set<Long> teamUserIds = teamMemberRepository.findByTeamId(teamId).stream()

if (!teamUserIds.containsAll(participantIds)) {
    throw new CustomException(ErrorCode.TEAM_NOT_MEMBER);
}

MeetingMember owner = MeetingMember.builder()

        .build();
meetingMemberRepository.save(owner);

안건 계층 구조 조회 설계

문제

상위 안건과 하위 안건으로 이어지는 구조를 개별 조회로 풀면 계층이 깊어질수록 쿼리 비용과 응답 복잡도가 커졌습니다.

해결

특정 회의의 안건을 한 번에 조회한 뒤 부모 안건 기준으로 메모리에서 그룹핑해 트리로 조립하고, 브랜치 수를 함께 집계했습니다.

성과

안건 트리와 브랜치 수를 프론트가 바로 사용할 수 있는 응답으로 제공하는 경험을 확보했습니다.

List<Issue> allIssues = issueRepository.findByMeetingIdOrderByCreatedAtAsc(meetingId);

List<Long> issueIds = allIssues.stream().map(Issue::getId).toList();
Map<Long, Long> branchCountMap = branchRepository.countByIssueIds(issueIds).stream()
        .collect(Collectors.toMap(
                row -> (Long) row[0],
                row -> (Long) row[1]
        ));

Map<Long, List<Issue>> childrenMap = allIssues.stream()
        .filter(issue -> issue.getParentIssue() != null)
        .collect(Collectors.groupingBy(Issue::getParentIssue));

브랜치 활동량 집계와 상태 전이 처리

문제

브랜치 화면은 이름과 설명만이 아니라 실제 활동량과 채택/기각 상태가 함께 보여야 했고, 집계 방식이 중요했습니다.

해결

브랜치 전용 집계 리포지토리를 두고 커밋 수를 한 번에 계산해 응답에 매핑했으며, 채택/기각 시 상태 전이와 알림을 함께 연결했습니다.

성과

브랜치 화면이 단순 제안 목록이 아니라 실제 활동이 보이는 협업 단위로 동작하게 됐습니다.

List<Object[]> rows = em.createNativeQuery("""
        SELECT scope_id AS branchId,
               COUNT(*) FILTER (WHERE chat_type IS NOT NULL) AS commitCount
          FROM chats
         WHERE scope_type = 'BRANCH'
           AND scope_id IN (:branchIds)
         GROUP BY scope_id
        """)
        .setParameter("branchIds", branchIds)
        .getResultList();

알림 저장 + 실시간 전달 구조

문제

회의 초대, 회의 시작, 브랜치 제안, 제안 수락/기각 같은 이벤트는 즉시 전달되어야 하고, 나중에 다시 볼 수 있는 이력도 필요했습니다.

해결

알림을 DB에 저장하고, 생성 직후 WebSocket으로 즉시 푸시했습니다. 읽음 여부, 전체 읽음, 삭제, 미읽음 카운트도 함께 관리했습니다.

성과

이벤트 발생 → 저장 → 즉시 전달 → 읽음 관리 흐름을 갖춘 독립적인 알림 도메인을 구현했습니다.
